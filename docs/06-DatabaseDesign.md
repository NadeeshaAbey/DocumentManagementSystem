# Database Design

## Version

- **Version:** 1.0
- **Status:** Draft

---

# Overview

Version 1 uses a relational database to store document metadata.

The physical document files are stored separately from the database. The database stores document metadata together with a storage key that uniquely identifies the stored file. The storage implementation is an infrastructure concern and may change without affecting the domain model.

This separation keeps the database small while allowing the storage implementation to change in future versions.

---

# Design Goals

- Store document metadata efficiently.
- Keep metadata independent from file storage.
- Ensure every document has a unique identifier.
- Support future features with minimal schema changes.

# Documents Table

| Column | Data Type | Required | Description |
|---------|-----------|----------|-------------|
| Id | UNIQUEIDENTIFIER | Yes | Primary key |
| OriginalFileName | NVARCHAR(255) | Yes | File name provided by the user |
| StoredFileName | NVARCHAR(255) | Yes | Generated unique file name |
| ContentType | NVARCHAR(100) | Yes | MIME type |
| FileSize | BIGINT | Yes | File size in bytes |
| StorageKey | NVARCHAR(255) | Yes | Unique identifier used by the storage provider |
| UploadedAt | DATETIME2 | Yes | Upload timestamp |
| LastModifiedAt | DATETIME2 | Yes | Last modification timestamp |

# Primary Key

## Id

A GUID is used as the primary key.

### Reason

- Globally unique.
- Easy to generate in the application.
- Avoids exposing sequential identifiers.
- Suitable for future distributed deployments.

|---------|--------|

# Constraints

## Required Fields

The following columns cannot be NULL:

- Id
- OriginalFileName
- StoredFileName
- ContentType
- FileSize
- StorageKey
- UploadedAt
- LastModifiedAt

---

## File Size

- Must be greater than zero.
- Must not exceed the configured maximum upload size.

---

## Original File Name

- Cannot be empty.
- Does not need to be unique.

---

## Stored File Name

- Must be unique.
- Generated by the system.
- Never entered by the user.

---

# Data Lifecycle

## Create

1. Upload file.
2. Store file on disk.
3. Insert metadata into the database.

---

## Read

Retrieve metadata from the database.

Use the storage key to retrieve the physical file through the configured storage provider.

---

## Delete

1. Delete the physical file.
2. Delete the metadata record.

Both operations should succeed together to avoid orphaned data.

# Design Decisions

## Why separate metadata from the file?

Advantages:

- Faster database queries.
- Smaller database size.
- Easier backup strategies.
- Storage implementation can change independently.

---

## Why store the original filename?

The original filename is displayed to users.

The stored filename is an internal implementation detail.

---

## Why store the content type?

Allows clients to:

- Display document type.
- Return the correct HTTP Content-Type during downloads.
- Validate supported file formats.

---

## Why store the storage key?

The application stores only a storage key, not a physical path.

Examples:

- documents/8e94b5d3.pdf
- documents/2026/07/report.pdf

The infrastructure layer is responsible for translating this key into an actual storage location.

This approach provides several advantages:

- The domain remains independent of the storage implementation.
- Switching from local storage to Azure Blob Storage requires changes only in the Infrastructure layer.
- Database records remain valid even if the physical storage location changes.
- Business logic never depends on file system paths or cloud-specific URLs.

---

# Version 1 Scope

The database intentionally does **not** include:

- Users
- Roles
- Permissions
- Folders
- Categories
- Tags
- Version history
- Audit logs
- Soft deletes

These features will be added incrementally as the system evolves.
